# rodauth-admin audit, 2026-09-28

**22 verified findings (1 high, 6 medium, 15 low). The most important: admin sign-in checks any production password before the allowlist, and the only brute-force ceiling (the TOTP failure limit) has no test.**

Every finding below was adversarially verified by independent reviewers; the consensus line shows how many agreed. Findings fixed since the audit carry a **Status** line linking the PR. Findings without one were open when this file was committed.

## Security

### [Medium] Admin sign-in is a lockout-free password oracle and account enumerator over the whole authdb
- **Status:** fixed in [onetimesecret/rodauth-admin#21](https://github.com/onetimesecret/rodauth-admin/pull/21)
- **Location:** `lib/rodauth_admin/auth.rb:139` (broken-authentication)
- **Why it matters:** The allowlist check runs in `after_login`. Rodauth only reaches that hook after `account_from_login` has found the row, `open_account?` has passed and `password_match?` has succeeded (rodauth 2.47.0 `features/login.rb:57-84`). The admin instance deliberately leaves `:lockout` off. As a result, POST `/login` gives an unthrottled argon2/bcrypt check against all ~200k production accounts and bypasses the tenant's 5-try lockout. Each outcome also returns a different message: no matching login, unverified account, invalid password, and "not an operator". Anyone who can reach the tunnel can therefore find out which emails exist, which are verified, and whether a password is correct for a non-operator. A correct guess is even written to production's auth log as a successful login. The SSH tunnel and TOTP limit what an attacker can do inside the admin, but the credential confirmed here is the customer's real production password.
- **Suggested fix:** Refuse before the password is ever checked. Add a `before_login_attempt` that calls `throw_error_reason(:no_matching_login, ...)` when `RodauthAdmin::Allowlist.allowed?(account_id)` is false, or override `account_from_login` to join `admin_operators`. Set `no_matching_login_message`, `invalid_password_message` and `unverified_account_message` to the same generic string. Keep the `after_login` denial as a second check. Consider an IP/email rate limit (for example rack-attack) on POST `/login`.
- **Consensus:** 3/3 verifiers

### [Low] `rodauth_admin_app` can UPDATE `account_otp_keys.key`, so it can re-key any production account's TOTP
- **Location:** `db/grants/postgres/rodauth_admin_roles.sql:175` (excessive-privilege)
- **Why it matters:** The grant is table-wide, not limited to specific columns. The same file refuses UPDATE on this table to the verbs role precisely because such a role "could quietly re-key an operator's second factor" (lines 333-335). The most exposed credential, the one behind the unauthenticated `/login` and `/otp-auth` endpoints, still has that power over every row. Rodauth's otp feature only ever writes `last_use` and `num_failures`. `spec/grants_spec.rb` does not check this limit.
- **Suggested fix:** Run `REVOKE UPDATE ON account_otp_keys FROM rodauth_admin_app;`, then `GRANT SELECT, INSERT ON account_otp_keys ...` and `GRANT UPDATE (last_use, num_failures) ON account_otp_keys ...`. Add a grants_spec example asserting that `UPDATE account_otp_keys SET key = ...` is refused.
- **Consensus:** 3/3 verifiers

### [Low] The `ARGON2_SECRET` pepper stays in the process environment and is not required in production
- **Location:** `lib/rodauth_admin/auth.rb:81` (secret-handling)
- **Why it matters:** `Env.auth_secret` removes AUTH_SECRET and AUTH_OLD_SECRET from ENV after reading them. That keeps them out of `/proc/<pid>/environ`, child processes and error-reporter dumps. The argon2 pepper protects production password hashes just as directly, but it is read with `ENV.fetch` and stays in ENV. It is also missing from `Env.validate!`. A production deploy without the pepper boots cleanly, and every argon2 login then fails. The problem shows up as operators being locked out instead of at boot.
- **Suggested fix:** Add `Env.argon2_secret`, which reads the value with `ENV.delete` and raises `ConfigurationError` in production when it is missing. Call it from `validate!` and reference it in the configure block.
- **Consensus:** 2/3 verifiers

## Correctness

### [Low] `operators:add` picks an arbitrary row when an email has several accounts and can abort spuriously
- **Location:** `Rakefile:69` (correctness)
- **Why it matters:** The unique index on `accounts.email` only covers open statuses (1 and 2). One address can therefore belong to both a closed account and a later Verified one. The lookup `where(email:).first` has no status filter and no ORDER BY. If the closed row comes back first, the task aborts with "not Verified (status_id=3)". `Allowlist.account_id_for_email` (`allowlist.rb:35`) has the same problem, so `operators:remove` sometimes succeeds and sometimes raises `AmbiguousEmail` for the same input.
- **Suggested fix:** Limit both lookups to open accounts: `status_id: 2` in the Rakefile, and `select_map(:id)` over `OPEN_STATUS_IDS` in Allowlist. Raise `AmbiguousEmail` on more than one match instead of relying on storage order.
- **Consensus:** 3/3 verifiers

### [Low] A missing identity is reported as "No account has id N"
- **Location:** `lib/rodauth_admin/verb_routes.rb:186` (error-handling)
- **Why it matters:** `Verbs.unlink_identity` raises `NotFound` both when the account is missing and when the identity is. `verb_execute` maps every `NotFound` to the account-missing page. In the common race, where the customer unlinked the provider between the confirm GET and the POST, the operator is told the account is gone and gets no link back to it. `verb_confirm` has the same problem for a stale identity id.
- **Suggested fix:** Add a `Verbs::IdentityNotFound` subclass, rescued to a 404 that names the identity and links to `account_path(id)`. Alternatively, pass identity context into `missing` so the template can say the identity is no longer linked.
- **Consensus:** 3/3 verifiers

## Test coverage

### [High] `otp_auth_failures_limit` (7), the stated brute-force ceiling, has no test
- **Status:** fixed in [onetimesecret/rodauth-admin#21](https://github.com/onetimesecret/rodauth-admin/pull/21)
- **Location:** `lib/rodauth_admin/auth.rb:97` (security-untested)
- **Why it matters:** With lockout dropped, the header comment names TOTP failures on the shared key row as a brute-force ceiling. No spec submits wrong TOTP codes. Nothing asserts that `num_failures` increments, that the 8th attempt is refused even with a correct code, or that an operator already locked on the tenant side is refused. A regression that disabled the limit would remove the admin's only rate limit and CI would still pass.
- **Suggested fix:** In `spec/sign_in_spec.rb`, sign in, log out, log in again and post 7 wrong codes to `/otp-auth`. Assert `num_failures == 7`. Then post a correct ROTP code and assert it is refused and `/` still redirects to `/otp-auth`. Also assert the `rodauth-admin: otp_auth_failure` audit rows.
- **Consensus:** 2/3 verifiers

### [Medium] The `mfa_fresh?` future-stamp guard and non-Integer branch are untested
- **Status:** fixed in [onetimesecret/rodauth-admin#22](https://github.com/onetimesecret/rodauth-admin/pull/22)
- **Location:** `lib/rodauth_admin/auth.rb:217` (security-untested)
- **Why it matters:** The existing spec only moves the clock forward past the window. A refactor from `age.between?(0, ...)` to `age <= ...` would reopen the "forward clock jump mints an unbounded window" hole that the comment describes, and CI would stay green.
- **Suggested fix:** Add an example where `Time.now` is stubbed 60s back, so the stamp is in the future: the GET redirects to `/otp-auth` and the POST does not delete. Add a second example with `session['mfa_at']` set to a String and to nil, asserting `mfa_fresh?` is false.
- **Consensus:** 2/3 verifiers

### [Medium] The argon2 pepper path and the `hmac_old_secret` rotation path never run in tests
- **Status:** fixed in [onetimesecret/rodauth-admin#22](https://github.com/onetimesecret/rodauth-admin/pull/22)
- **Location:** `lib/rodauth_admin/auth.rb:81` (security-untested)
- **Why it matters:** `spec_helper.rb:56` deletes ARGON2_SECRET, so production's peppered configuration is never exercised. If the pepper were wired wrong, every operator would be locked out, and the first sign would come at deploy time. Rotation under AUTH_OLD_SECRET is not proven either.
- **Suggested fix:** Add a spec with a peppered fixture hash. `login!` should succeed with the pepper and fail without it. Add a rotation example: enroll under AUTH_SECRET=A, reboot with B plus OLD=A, and assert otp-auth still verifies.
- **Consensus:** 3/3 verifiers

### [Medium] `Env` has no tests: production fail-closed raises, secret length and `ENV.delete` are unverified
- **Status:** fixed in [onetimesecret/rodauth-admin#22](https://github.com/onetimesecret/rodauth-admin/pull/22)
- **Location:** `lib/rodauth_admin/env.rb:143` (untested-config-guards)
- **Why it matters:** Every boot-time safety check lives in `env.rb`, and none of them is tested:
  - `session_secret` raises when unset or shorter than 64 bytes.
  - `dev_default` raises in production.
  - `auth_secret` raises when unset and deletes the secret from ENV.
  - Trailing slashes are stripped from `colonel_console_url`.
  - `validate!` must call all of the above.

  The suite always runs with `RACK_ENV=test`, so every production branch goes unexercised in CI.
- **Suggested fix:** Add `try/env_try.rb` covering: `production?` defaults, each raise, the 63/64-byte boundary, `ENV['AUTH_SECRET']` being nil after the read, slash stripping, and `validate!` raising for each missing value. Reset the memoized ivars between cases.
- **Consensus:** 3/3 verifiers

### [Medium] A verb POST against an unreachable authdb is neither rescued nor tested, despite the header comment
- **Status:** fixed in [onetimesecret/rodauth-admin#23](https://github.com/onetimesecret/rodauth-admin/pull/23)
- **Location:** `lib/rodauth_admin/verb_routes.rb:181` (error-path-untested)
- **Why it matters:** The `verbs.rb` header (lines 43-46) says the web layer renders a degraded panel. In fact `Sequel::DatabaseError` and `PoolTimeout` fall through to the generic 500 handler. The confirm-page degraded branch (`verb_confirm` lines 163-164, `verb.erb` 263-269) is also untested. How the most dangerous screens behave during an outage is untested and contradicts the documentation.
- **Suggested fix:**
  1. Stub `Database.verbs` to raise on transaction. Assert the chosen status, and that no `admin_actions` row or deletion occurs.
  2. Stub `Verbs.preview` as unavailable. Assert a 200 with "This account is unavailable" and no `<form>`.
  3. Pick one behaviour, either a 500 or a rescue of `Database::UNAVAILABLE_ERRORS`, and align the comment with it.
- **Consensus:** 3/3 verifiers

### [Medium] The PostgreSQL privilege-boundary spec skips silently when its preconditions drift
- **Status:** fixed in [onetimesecret/rodauth-admin#24](https://github.com/onetimesecret/rodauth-admin/pull/24)
- **Location:** `spec/grants_spec.rb:89` (silent-skip)
- **Why it matters:** This spec is the only verification of the grants file. It `skip`s the whole group when the adapter is not Postgres or the four URLs are not distinct. A `ci.yml` edit could make `ADMIN_DATABASE_URL_RO` fall back to the app URL through the `||=` in `spec_helper.rb:405`, or reorder the grant step. Either change would turn every example into a pending skip while the job stays green.
- **Suggested fix:** Set an opt-in flag, for example `RODAUTH_ADMIN_EXPECT_GRANTS=1`, only in the test-postgres job. When the flag is set, `raise` instead of `skip`. Also assert that `opts[:user]` on each connection is the expected role name.
- **Consensus:** 2/3 verifiers

### [Low] The `operator_account?` fail-closed rescue is untested
- **Location:** `lib/rodauth_admin/verb_routes.rb:261` (fail-closed-untested)
- **Why it matters:** When `admin_operators` cannot be read, the method returns true. That hides the two MFA verbs on the account page and flags them on the confirm page. Two regressions would go unnoticed: changing the return to `false` (fail open), or dropping the rescue (a 500 on every account page during an outage).
- **Suggested fix:** Use the SimpleDelegator pattern to make `Database.readonly` raise on `:admin_operators`. Assert that `/accounts/<id>` returns 200 without the disable-mfa or regenerate-recovery-codes links but still shows clear-lockout. Assert that the disable-mfa confirm submit is disabled.
- **Consensus:** 3/3 verifiers

## Dead code

### [Low] `timecop` is declared but never used
- **Location:** `Gemfile:93` (dead-dependency)
- **Why it matters:** No spec or tryout requires it. `sign_in_spec.rb:124` even explains why Timecop cannot help. By the Gemfile's own header, every dependency is "one more thing to audit".
- **Suggested fix:** Remove the line and run `bundle install`.
- **Consensus:** 3/3 verifiers

### [Low] `rack-protection` is bundled but nothing requires or mounts it
- **Location:** `Gemfile:32` (dead-dependency)
- **Why it matters:** Nothing in lib/, config.ru, spec/ or try/ requires or mounts it, and neither roda nor rodauth loads it. CSRF protection already comes from Roda's `route_csrf`.
- **Suggested fix:** Delete the line. If the intent was to use it, add `use Rack::Protection` in `config.ru` together with a spec.
- **Consensus:** 3/3 verifiers

### [Low] `plugin :halt` is loaded but unused
- **Location:** `lib/rodauth_admin/app.rb:48` (unused-plugin)
- **Why it matters:** The plugin only extends `halt` so it can take a status, body or headers. No code calls `r.halt` at all. Rodauth's own `request.halt` takes no arguments, and route_csrf uses `throw :halt`.
- **Suggested fix:** Delete `plugin :halt`. Add it back if a handler ever needs `r.halt status, body`.
- **Consensus:** 3/3 verifiers

### [Low] `AccountDetail.timeline` takes a `now:` keyword that nothing passes or reads
- **Location:** `lib/rodauth_admin/account_detail.rb:242` (dead-parameter)
- **Why it matters:** The keyword suppresses a RuboCop rule to keep a call shape that no caller relies on. Relatedly, `sections` builds `QueryFailure` with a `page:` field that only the timeline reads (line 316).
- **Suggested fix:** Drop `now: nil` and the RuboCop disable. Optionally give `page:` a default in the Data definition.
- **Consensus:** 2/3 verifiers

### [Low] `req` is passed through `render_verb` and `show_codes`, and both ignore it
- **Location:** `lib/rodauth_admin/verb_routes.rb:161` (dead-parameter)
- **Why it matters:** Both callees name the parameter `_req`, so it is dead across three method signatures.
- **Suggested fix:** Remove it from `show_codes`, `render_verb` and `verb_confirm`, and from their call sites (lines 142-153 and 188-195).
- **Consensus:** 3/3 verifiers

### [Low] The `limit:` keyword on `regenerate_recovery_codes` is never supplied
- **Location:** `lib/rodauth_admin/verbs.rb:244` (dead-parameter)
- **Why it matters:** No caller passes it. It is also a knob that could mint more codes than the 4 the tenant promises.
- **Suggested fix:** Remove the keyword and use `RECOVERY_CODES_LIMIT` directly, or add a tryout if the override is meant to stay.
- **Consensus:** 2/3 verifiers

### [Low] `rodauth_admin_app` is granted SELECT on `account_statuses`, which nothing on that credential reads
- **Location:** `db/grants/postgres/rodauth_admin_roles.sql:128` (stale-grant)
- **Why it matters:** Every reader of the table runs on `Database.readonly`, and Rodauth never joins it. This violates the file's own rule that "a grant nothing exercises is a grant nobody notices going stale".
- **Suggested fix:** Grant only `SELECT ON accounts`, add a guarded `REVOKE SELECT ON account_statuses FROM rodauth_admin_app`, and update `docs/design/database-credentials.md:14`.
- **Consensus:** 3/3 verifiers

### [Low] `rodauth_admin_app` is granted SELECT on `admin_schema_info`, which only the migrator reads
- **Location:** `db/grants/postgres/rodauth_admin_roles.sql:188` (stale-grant)
- **Why it matters:** The table is only read by the migrator and by `Rakefile:26`, both on the migrator connection. `check_admin_schema!` only probes `admin_operators` and `admin_actions`.
- **Suggested fix:** Delete the grant and add a guarded REVOKE.
- **Consensus:** 3/3 verifiers

### [Low] The design doc says the verbs role can SELECT `account_statuses`, which the grants file excludes
- **Location:** `docs/design/database-credentials.md:16` (stale-doc)
- **Why it matters:** The document that describes the privilege boundary contradicts the file that implements it (grants lines 306-331).
- **Suggested fix:** Change the row to "SELECT on `accounts`, `admin_operators` and every table it mutates".
- **Consensus:** 2/3 verifiers

### [Low] The quality-gates doc still says "four views" and ~1.4k lines
- **Location:** `docs/design/quality-gates.md:80` (stale-doc)
- **Why it matters:** There are now ten templates and lib/ is about 2.7k LOC. The "revisit when it grows" decisions for ERB linting and type checking rest on these outdated numbers.

- **Consensus:** 3/3 verifiers
